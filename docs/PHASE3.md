# Phase 3: LMS core, enrollment, progress, exams

**Status: all 116 Phase 3 HTTP operations in `api-contract.json` exist** (verified by comparing the running Swagger document with the contract; the certificate verify route differs only in its parameter name). Real limits are listed at the bottom. Phase 4 has not been started.

## What is built

- Source: `backend/src/SmartLMS.Infrastructure/Services/Lms/LmsService.cs` (catalog, courses, sections, lessons, enrollment, lesson access, progress), `AssessmentService.cs` (question banks, exams, attempts, grading), controllers `LmsController.cs` and `AssessmentsController.cs`.
- Course workflow: instructor creates a draft, submits it, a TenantAdmin approves (publishes) or rejects. Students and anonymous callers only see published courses.
- Write access: the course owner or a TenantAdmin. Any other instructor gets 404, so the course is not disclosed. Co-instructors and teaching assistants are supported through `PUT /courses/{id}/staff` (see Slice E).
- Lesson access (`GET /lessons/{id}`): students need a live enrollment (not revoked, not expired), or the lesson must be a free preview of a published course. Drip rules (by date, days after enrollment) and lesson prerequisites are enforced on the server and return 403 with a reason code. Prerequisite cycles and cross-course prerequisites are refused. The course outline never carries lesson content.
- Enrollment: free courses only. A paid course returns 402 `PAYMENT_REQUIRED` (payments are Phase 4). Parallel enroll calls create one row.
- Progress: heartbeat adds at most 300 watched seconds per call, completion recalculates percent, and the enrollment completes at 100%. Instructors now see a student through `InstructorScope` once that student is enrolled in the instructor's own course, and stop seeing them when the enrollment is revoked (tested).
- Exams: question types McqSingle, McqMulti, TrueFalse, FillBlank, Matching are auto-graded. ShortAnswer and Essay wait for manual grading by the course owner. The question set is frozen at attempt start. The timer is the server clock with a 15 second grace. Correct answers and explanations are never sent in an attempt, and students get score and pass state only (no per-question detail). Attempt limit is protected by the existing unique index on (ExamId, UserId, AttemptNumber). Submission is claimed atomically, so parallel submits grade once. A tab-switch limit voids the attempt.

## Slice B: parent portal, certificates, gamification, jobs

- Parent link: a student creates a signed 15-minute code (`POST /students/me/link-codes`). A Parent redeems it (`POST /parent/links`) and gets a Pending link. A TenantAdmin, or an instructor of a course the student is enrolled in, activates or revokes it. Activation is atomic and one code can activate only one parent. All bad codes get one refusal. A parent sees a student only through an Active link, and only summary numbers (course progress, average exam score, weekly study hours, risk alerts). Attendance is null because live sessions are not built. Alerts are computed when the parent reads them (low exam score, 14 days of inactivity), not by a background job.
- Certificates: issued once per student and course when the enrollment flips to Completed (atomic) or manually by the course owner or admin. Public verify returns holder name, course, date and status only. The PDF (`GET /certificates/{id}/pdf`) is drawn with SkiaSharp and HarfBuzz using the embedded **Amiri** font (SIL OFL 1.1, licence in `backend/src/SmartLMS.Infrastructure/Assets/Fonts/Amiri-OFL.txt`), so Arabic letters join and run right to left. Mixed Arabic/Latin text is split into direction runs (simplified bidi, not full UAX #9: no nested embeddings or explicit direction marks). Bold is synthetic (Amiri ships one weight). Text in other scripts that Amiri lacks (for example CJK) would show missing glyphs. The QR is vector squares. **The URL in the QR comes from `Certificates:VerificationBaseUrl`, never from the request Host header.** Outside Development it must be an absolute https URL or the PDF endpoint returns 500 `VERIFICATION_URL_NOT_CONFIGURED/INVALID`. In Development only, it falls back to the request URL (for example `http://localhost:5000`), which is for developers and must not be printed on a real certificate. Copy/search of the Arabic text in the PDF depends on the viewer (glyphs are embedded with a ToUnicode map, but shaped Arabic can copy in visual order).
- Slice C: notes, bookmarks, study sessions, learning paths (publish is TenantAdmin only; enroll is idempotent and grants only free courses), discussions (course-scoped, votes recounted from distinct users), announcements (course announcements notify enrolled students; tenant-wide is TenantAdmin only), notifications, push-token storage (FCM sending is NOT built), chat rooms and messages over REST (membership and live enrollment are checked on every call), live-session scheduling and attendance (the join URL must be https; non-staff get it only from the join endpoint, which records attendance once). No Zoom/Meet API calls. Messages are pushed through SignalR (Slice E).- Slice D: assignments (rubric, team mode, versioned submissions, rubric grading with per-criterion bounds, comments, return for resubmission) and peer review. Writers on one assignment are serialised by a transaction that first writes the assignment row, so parallel submits give distinct versions and parallel "assign peer reviews" calls cannot create extra reviews. Peer reviewers read only the work they were assigned, anonymously and without the grade. Team size is enforced after insert. NOT built: file attachments on submissions (text and https link only), plagiarism checks, AI provisional grading, and the "async job" for peer-review assignment (it runs inside the request).
- Fixed in this slice: a gamification race that could lose a lesson XP row when a streak row was created by a parallel request (found by the existing completion test failing once; the XP row is now saved before the streak).

## Slice E: realtime, jobs, question management, content authoring, files, badges

- **SignalR** hubs `/hubs/notifications`, `/hubs/chat`, `/hubs/live`. Browsers cannot send headers on WebSocket, so pass `?device_id=<device fingerprint>` in the URL; the SignalR client sends `access_token` itself from `accessTokenProvider`, and the tenant comes from the token. Every hub call re-checks the device, the active account and token expiry. Group names include the tenant id. Chat messages and announcement notifications are pushed. Live sessions: a student joining pushes a head count (`attendance`, count only, never names) to everyone in the session group, and scheduling a session notifies enrolled students. Notification types pushed live and stored: Announcement, ThreadReply, LiveSession, Graded, Returned, PeerReview, ExamGraded. Tests cover long polling and WebSockets (WebSocket with the token in the query string, as browsers must) against the in-memory test server; neither was run against Kestrel on a real network or a browser client.
- **Hangfire**: settings `Hangfire:Enabled`, `Hangfire:Storage` (`SqlServer` default, `InMemory` only outside Production), `Hangfire:Workers`. Recurring job `expire-enrollments` runs every 15 minutes. Tested inside a real Hangfire server with in-memory storage. SQL Server storage is NOT verified (no SQL Server here). The Hangfire dashboard is deliberately not exposed. Peer-review assignment still runs inside the request.
- **Question management**: bank list, question list with filters, update, delete (refused while a published exam uses the question), JSON and CSV import (all or nothing, 500 rows max, CSV has no Matching), exam update (refused when a published exam already has attempts).
- **Content authoring** (owner or TenantAdmin only, others get 404): course prerequisites (cycle refused, enforced when a student first enrolls: every prerequisite must be Completed, else 403 `PREREQUISITE_NOT_MET`), section and lesson reorder (the list must name every item once), chapters, slides, interactive video quiz points (question must belong to a bank of the same course; auto-graded types only). Students get the quiz without `IsCorrect`; the answer endpoint returns correct/incorrect, whether playback may continue (answered right, not required, or the skip-after-N-attempts rule) and the explanation only once allowed.
- **Lesson files** on local disk under `Storage:Root`: media upload (Video, Audio, Pdf lessons; mp4, webm, mp3, pdf by file signature, 200 MB default `Storage:MaxMediaBytes`), resources (pdf, png, jpg, zip by signature, 25 MB default), stream (range requests, same access rules as opening the lesson) and resource download (non-downloadable resources are for authors only). The file name and Content-Type the client sends are ignored. There is no virus scanning, no transcoding and no HLS or signed URLs.
- **Badges**: built-in `FIRST_LESSON`, `FIRST_COURSE`, `STREAK_7`, `XP_1000`, awarded after XP is written, once per user (unique index plus idempotent check). `Badge.RuleJson` is not used. There is no badge management endpoint (none is in the contract).

- **Course staff**: `PUT /courses/{id}/staff` (owner or TenantAdmin only; the user must hold the Instructor role for CoInstructor and the TeachingAssistant role for TeachingAssistant). A CoInstructor can author the course (sections, lessons, files, quizzes, banks, exams, assignments, live sessions, certificates), grade, and sees it in `courses/mine`; they cannot delete or submit the course or change staff. A TeachingAssistant can read the course and lessons, list and grade submissions and exam attempts, post announcements, take part in discussions and see attendance; they cannot author. All other courses return 404. Removing a staff row removes access at once. Rules live in `CourseAccess`.
- **Push to phones (FCM)**: `Push:Fcm:Enabled=true` plus `Push:Fcm:ServiceAccountPath` (a Firebase service-account JSON kept OUTSIDE the repo, set through user-secrets or an environment variable). Off by default; nothing is sent. Each notification is stored, pushed over SignalR, and sent to the user's latest 5 device tokens; a token FCM reports as unregistered is deleted. Tested against a fake HTTP server (signed JWT verified, access token cached, dead token, server error). NOT run against the real FCM service. Push is sent inside the request (5 s timeout per call, failures ignored) and at most 500 recipients per announcement are pushed live.

- **Peer-review assignment job**: `POST /assignments/{id}/peer-reviews/assign` creates a `BackgroundJobs` row (type `PeerReviewAssign`, tracked at `GET /jobs/{id}`, visible to the requester and TenantAdmin) and queues it in Hangfire; the response returns `jobId` and `queued: true` before the work runs. A second call while a job is open returns that job. The work is serialised per assignment and idempotent, so retries (2 automatic) and repeats create no extra reviews. A failure ends the job as Failed with a short message. Reviewers get a PeerReview notification when it finishes.
- **Schema change and migration**: the `BackgroundJobs.Type` check constraint gained `PeerReviewAssign`. Changed in `docs/generator/spec_schema.py`, regenerated with `gen_schema.py` and `gen_csharp.py` (`reconcile_ef.py`: 0 differences), and a new EF migration `20261124161458_PeerReviewJobType` drops and re-adds that one constraint (Up and Down). `docs/ef-migration.sql` is regenerated (idempotent). The migration was generated with `dotnet ef` and is NOT applied to a live SQL Server here; existing databases need `dotnet ef database update` or the script.

## Remaining real limits

- Peer-review assignment is a Hangfire job (see Slice E). With `Hangfire:Enabled=false` it runs inside the request instead, and the job row is already Completed.
- Hangfire SQL Server storage and the generated migrations are unverified on a live SQL Server and on Windows.
- Files are on local disk only: no virus scan, transcoding, HLS or signed URLs.
- Certificate PDF uses simplified bidi; FCM is unverified against the real service; email is never sent.
